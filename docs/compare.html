Where this fits.

People arrive here already comparing something. This page is the comparison, written to be checkable rather than flattering: approaches weighed against each other, the questions that actually decide the choice, and the things this project is honestly worse at.

No feature grids against named products. Those go stale in a week and are usually written by whoever is selling the thing. Where a neighbour is named, it is to point at it, not to score it.

Four ways to run an agent on your own machine

Not brands — shapes. Most tools are one of these, and each one asks something different of you.

📦

A container-first agent stack

Docker or Compose, a database container, a web container, an agent runtime container. Choose it if you already live in Docker, you want someone else's images to maintain the moving parts, and a docker compose up is your idea of a clean install. You take on the daemon, the images, and a second filesystem to keep backed up.

🧩

An editor extension

The agent lives inside your IDE, reads the file you have open, and edits in place. Choose it if your work is one repository at a time and you want the agent beside the cursor. You take on a single editor's lifetime: close the laptop and the agent stops, and there is no fleet, no scheduler and no map of what ran while you were away.

💬

A self-hosted chat front-end

A good UI over a model, accounts for a household or a team, history that persists. Choose it if what you want is a private chat app. You take on that it is a chat app: conversation is the unit of work, and "go run this and report back" is not.

🧠

This: a console in plain PHP

One folder you drop on a web server. The model is asked to call tools in a fixed syntax, a harness fits that syntax to whichever model you point at, and a fleet of agents works behind routing charts, approvals and a live map. No Docker, no build, no database.

Seven questions that decide it

Ask these of any tool in this space, this one included. The right-hand column is this project's answer, so you can hold it to it.

What has to be installed before it boots?containers · runtime · build step · database

PHP 8 and a web server. No composer install, no npm run build, no DB server — state is JSON under storage/. Upload the folder and it runs.

Whose models can it use?

Any of them, hosted or local: OpenAI-compatible endpoints, Anthropic, Gemini, Ollama, LM Studio, OpenRouter, a model you are serving yourself. Switching model does not mean switching tool.

Where do the tools actually run?

On your machine, under a jail and an allowlist, with approvals per action and a kill switch. The default is that nothing dangerous is on.

What happens when the model gets the tool syntax wrong?

Near misses are read, not dropped. The harness learns the dialect a model settles into, so a malformed call is a repair, not a failed run.

Can more than one agent run at once?

Yes — a fleet, with routing, pipelines and a live map of who is doing what. This is the part most chat-shaped tools do not have, because chat is one turn at a time.

What leaves this machine?

What you send to your model provider, and nothing else. No telemetry, no licence check, no phone-home. Drive it entirely with models on localhost and nothing leaves at all.

What does it cost?

The PHP host you already have. Apache-2.0, no seat count, no hosted tier to upsell you into. You pay your model provider directly, or nothing if the model is local.

Three things that are unusual here

Stated as what they are, not as digs at anything else. It is a crowded space and most tools do most things well.

The harness fits the model. Most agents are written against one provider's tool-calling format and quietly degrade for everything else. Here the call format is discovered per model — the Training drill proves it in twelve calls, and the console keeps whatever won.

Distribution is a folder. No image to pull, no dependency tree to resolve, no build artifact to trust. The thing you audit is the thing that runs, and updating is the app replacing its own files with a rollback kept on disk.

  • One folder — no Docker, no Node, no database server
  • Every guard has a test that makes the real request
  • Refusals are documented, not discovered at 2am
  • Updates roll back on their own if the version disagrees
  • Deleting the folder is the whole uninstall

What you give up

The honest column. If any of these is a hard requirement, another shape is the better tool for you.

  • !No containers means no isolation theatre. The jail and the allowlist are real, but a container is a stronger wall than a PHP process. If you need per-agent kernel isolation, run it inside one.
  • !One maintainer. Releases are frequent and the changelog names what broke. Nobody is on call, and there is no support contract to buy.
  • !No team accounts. It is built for one operator with a token. Multi-user permissions are not a feature here.
  • !Not an IDE. If your work is one file under the cursor, an editor extension will feel faster.
  • !Parallel agents want Apache or PHP-FPM. On PHP's built-in server a single streamed reply holds the only slot.

How to check any of this in five minutes

Every claim above is something you can verify without trusting this page.

Read the guards

The refusals are in the docs, and each one has a test that makes the real request against a throwaway copy of the tree.

git clone https://github.com/autonomous-loop-studio/Autonomous
cd Autonomous
php tests/run.mjs

Watch it refuse

Point it at a model, leave the tools off, and try to make it run one. Off is off by construction, not by prompt.

Run it, then delete it
